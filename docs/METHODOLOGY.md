# itol-cli 绘图方法论（2026-11-06）

> 定位：同行已无参考方向，本文档是 itol-cli 的方法论根基——把「什么是好的树图」编码进工具，
> 让 itol-cli 从「iTOL 的壳」变成「方法论编码的工具」。五个问题：绘图方法论 / 图片迭代方法论 /
> 绘图美学参数经验 / 各种树要展现什么 / 如何尽可能多展示信息。

---

## 一、绘图方法论：树图的本质是「论证一个进化主张」

一棵系统发育树图**不是数据展示，是论证**。它要回答的核心问题是「这些实体之间的进化关系是什么」，而每张论文图都在为**一个具体主张**服务：

- 「这个基因家族有 5 个亚家族」
- 「基因 X 的复制发生在物种分化之前」
- 「这个亚家族在豆科里特异性扩张了」

**方法论第一原理：主张决定注解，不是数据决定注解。**

推论：
1. **先问主张，再选注解**。主张是「5 个亚家族」→ 亚家族色带是**主注解**，必须视觉最强；主张是「复制时机」→ 时间轴+支持度是主注解。itol-cli 的 gen 场景库本质就是「主张→注解方案」的映射表。
2. **每张图有一个注意力预算**。注解层数每 +1，可读性就扣一分。方法论问题不是「能加多少」，而是「证明主张所需的最小注解集是什么」。**itol-cli 应该有「主张优先」的默认克制**——宁缺毋滥。
3. **视觉层级 = 论证层级**。主注解（最大/最醒目）→ 支撑注解 → 背景注解。读者眼睛应该被引导到主张上。

## 二、图片迭代方法论：好图是迭代出来的，关键在迭代成本

出版级图不是一次画对的，是**迭代收敛**出来的。瓶颈不在「会不会画」，在「每一轮迭代多快多便宜」。

**迭代方法论（把用户的自评分美学循环编码成一等公民流程）：**

```
生成 N 个变体 → 评分（对照标准）→ 选最优 → 调参 → 再生成
```

每一轮的收敛判据（可机器化）：
- **可读性**：叶标签在最终图幅下可读？（字号 vs 叶数）
- **主张可见性**：主张注解是否一眼可见？
- **信噪比**：有没有 chartjunk（冗余网格/装饰/重复信息）？
- **色彩可区分**：相邻组的颜色能不能分清？色盲友好？

**itol-cli 的差异化方向：`itol iterate`——把迭代闭环做成命令。**
- 生成 K 个参数变体（调色板 × 色带宽 × 字号 × 布局）→ 批量渲染 → 对照标准自评 → 输出最优 + 各变体对比。
- 这正是用户已有的自评分美学工作流，把它从「手工循环」固化成「工具内建」。
- 配套：session/replay（每次迭代的参数+输入哈希留痕，改一个参数能重放全流水线——PyiTOL 的 replay 思路）。

## 三、绘图美学参数经验（生信树图的实证经验值）

这是「手感」的显式化——把审稿人/老手默认知道的参数经验写成可执行规则：

### 尺寸与可读性（硬约束）
| 参数 | 经验值 | 依据 |
|:---|:---|:---|
| 叶标签字号 | 最终图幅下 ≥6pt（理想 8-10pt） | 期刊 2 栏图 ~180mm 宽；50 叶树 8-10pt 可读，200 叶不可读 |
| 叶数→布局 | <60 叶矩形 / 60-200 叶考虑环形 / >200 叶环形+折叠或分子树 | 矩形标签可读性最高，环形省空间但牺牲标签 |
| 色带宽度 | 图幅宽的 2-3% | 太细看不见，太粗喧宾夺主 |
| 枝线宽 | 0.5-1pt | 太细印刷丢失，太粗糊成一团 |
| 图例 | 必须有，放不挡树的位置（iTOL 默认 bottom-right 会避） | 色带没图例=读者猜谜 |

### 色彩（期刊事实标准）
- **分类色板**：≤10-12 组用离散色（NPG 鲜艳 / Okabe-Ito、Tol 色盲安全——现在期刊普遍要求色盲友好）；>12 组强行区分会糊，应该**合并小组或改用渐变/层级**。
- **连续数据**（表达量/选择压力/dN/dS）：用发散或顺序色标（红蓝发散表正负，viridis 表大小），别用分类色。
- **背景**：白底（透明 PNG 在很多查看器里显黑——itol-cli 已踩过这个坑，-b white）。

### 支持度展示（大树的关键决策）
- **不要在千叶树上标所有 bootstrap 值**——满树数字=噪点。
- 策略：阈值过滤（只显示 <90 的弱支持）/ 符号大小编码（点大小=支持度）/ 枝宽编码。itol-cli 的 bootstrap 场景模板已有四态，应默认「只标弱支持」。

## 四、各种树要展现什么信息（主张→注解的映射）

不同树承载不同主张，注解集完全不同：

| 树类型 | 主张 | 主注解 | 支撑注解 | 别加 |
|:---|:---|:---|:---|:---|
| **基因家族树**（用户主战场） | 亚家族划分/扩张 | 亚家族色带 | 支持度、物种来源色、结构域、选择压力、表达热图 | 别同时堆 5+ 层 |
| **物种树** | 分化时间/关系 | 时间轴（timescale） | 支持度、化石标定 | — |
| **系统发育地理** | 地理聚类 | 地理色带/标签色 | 支持度 | — |
| **基因树vs物种树调和** | 复制/丢失事件 | D/L 事件标记 | 物种树背景 | — |

**itol-cli 方向：gen 场景 = 树类型 × 主张的预设注解组合**。当前 9 场景是按「注解类型」组织，更方法论的组织是按「树类型 × 主张」——比如 `gene-family-expansion`、`gene-family-subfamily`、`species-tree-timescale`。

## 五、如何尽可能多展示信息（信噪比约束下的密度最大化）

Tufte 原则：**最大化 data-ink ratio**（数据墨比）——每一滴墨都承载信息，删掉不承载信息的墨。

树图的多层注解（一棵树同时带：亚家族色带 + 支持度符号 + 表达热图 + 结构域 + 基因计数条形图）是把一棵树变成「多维数据面板」的正当手段——但每层都吃注意力预算。

**密度最大化的方法论（不是堆，是结构化）：**
1. **共享叶轴对齐**：树 + 对齐的数据面板（热图/条形/点图）共享叶序轴——ggtree 的 geom_facet 思想。这是「一棵树带 N 组数据」且不乱的唯一正道（iTOL dataset 也是这个模型，但版式控制弱）。
2. **编码通道分工**：颜色→分类（亚家族）、符号大小→数值（支持度）、热图→矩阵（表达）、位置→结构域。**一个通道只编一种信息，别复用**（颜色既表亚家族又表支持度=灾难）。
3. **大树的唯一解是聚合**：>200 叶不可读，策略=折叠单系群为三角、只展关键支、或拆成多面板。**itol-cli 应该主动拦「千叶环形 + 全标签 + 5 层注解」这种必糊组合**。

## 六、落地为 itol-cli 的方法论编码（突破方向）

把上面五条变成 itol-cli 的差异化能力（这才是「最好的那个」的护城河）：

| # | 方法论 | itol-cli 落地点 |
|:--|:--|:--|
| 1 | 主张决定注解 | gen 场景按「树类型×主张」组织 + `itol plan`（说主张→推荐注解组合） |
| 2 | 迭代闭环 | `itol iterate`（参数变体×渲染×自评→最优）；session/replay 留痕 |
| 3 | 美学参数默认 | 字号/色带宽/布局按叶数自动适配（可读的默认）；色彩默认色盲友好 |
| 4 | 树类型×主张 | gen 场景从「注解类型」升级为「主张预设」 |
| 5 | 密度护栏 | lint/plan 警告「叶数×注解层数×布局」的必糊组合 |
| 6 | 可读性硬约束 | render 前自动检查：叶数 vs 字号 vs 图幅 → 报「标签将不可读」 |

**核心转向：itol-cli 不再只是「帮你生成 iTOL 注解文件」，而是「编码了树图方法论的工具」——它知道什么是好图，并默认把你往好图方向推。** 这是同行（itolapi/PyiTOL/itol.toolkit）都没做的层。
